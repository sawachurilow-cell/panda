# Витрина-киоск (storefront)

Сенсорная витрина для покупателя поверх **B2B API i-t-p.pro** (JSON-RPC, версия 2.17).
Импортируется в сенсорный киоск и открывается как обычный сайт: покупатель листает
каталог, собирает корзину и оформляет заказ.

Игра `../index.html` этот код не трогает — витрина полностью изолирована в папке `storefront/`.

## Почему бэкенд-прокси, а не прямые вызовы API из киоска

B2B API **нельзя** дёргать напрямую из браузера киоска. Три блокера:

1. **Секреты.** Авторизация по логину/паролю → сессия. Во фронтенде киоска код и трафик
   доступны любому — учётка утечёт. Пароль/сессия живут только на сервере.
2. **Лимиты.** Каталог `2/час`, цены `get_active_products` **`10/час`**, логин `10/мин`.
   Если каждый покупатель тянет данные напрямую, лимит выгорает за минуты и API
   перестаёт отвечать. Поэтому данные тянет **один** бэкенд по расписанию и кэширует.
3. **Оптовые цены.** `price` / `rrp` / `wish_price` — дилерские, не розничные. Бэкенд
   применяет розничную наценку прежде, чем отдать цену в витрину.

```
   [ B2B API i-t-p.pro ]          одна сессия, редкие вызовы строго по лимитам
            ▲
            │  server/b2bClient.js
   [   наш бэкенд-прокси   ]        кэш каталога/цен, наценка, скрытые секреты
            ▲
            │  чистый локальный REST (server/routes/*)
   [  фронтенд киоска  ]            public/ — сенсорный UI, знает только наш бэкенд
```

## Структура

```
storefront/
├── README.md               ← этот документ (план + архитектура)
├── package.json
├── .env.example            ← пример настроек (скопировать в .env)
├── server/
│   ├── index.js            ← Express: отдаёт REST + статику фронтенда
│   ├── config.js           ← конфигурация из env, лимиты, TTL кэша
│   ├── b2bClient.js        ← клиент B2B API (login/сессия, каталог, цены, заказы)
│   ├── cache.js            ← TTL-кэш с single-flight (не превышает лимиты API)
│   ├── pricing.js          ← опт → розница (наценка); правило вынесено сюда
│   ├── catalogService.js   ← сборка витринного каталога (товары + цены + фото)
│   ├── mockData.js         ← демо-данные: фронтенд рендерится без реальной учётки
│   └── routes/
│       ├── catalog.js      ← GET /api/catalog/*
│       └── orders.js       ← POST /api/orders
└── public/                 ← фронтенд киоска (сенсорный, full-screen)
    ├── index.html
    ├── styles.css
    └── app.js
```

## Соответствие эндпоинтов B2B API → наш бэкенд

| Витрина (наш REST)                | Источник в B2B API                                   | Кэш |
|-----------------------------------|------------------------------------------------------|-----|
| `GET /api/catalog/categories`     | статика `catalog_tree_{id}.json` (1/мин, ночью)      | сутки |
| `GET /api/catalog/products`       | статика `products_{id}.json` (2/час, ночью)          | сутки |
| `GET /api/catalog/products?category=` | + `get_active_products` (10/час) — цены/остаток  | 10 мин |
| `GET /api/catalog/product/:sku`   | products + `get_active_products` + изображения       | 10 мин |
| `POST /api/orders`                | `create` orders (данные клиента в `partner_comment`) → `client_update` order_items | — |

### Данные клиента в заказе

B2B-метод `create` принимает только `partner_comment` и `logistic_center` —
отдельных полей под ФИО/телефон/адрес в API нет. Поэтому форма оформления
(ФИО, телефон, адрес разгрузки, комментарий — первые три обязательны)
упаковывается в структурированный `partner_comment`:

```
Клиент: Иванов Иван Иванович
Телефон: +7 900 123-45-67
Адрес разгрузки: Москва, ул. Ленина, 1
Комментарий: Позвонить за час
— Заказ из киоска
```

## Запуск

```bash
cd storefront
npm install
cp .env.example .env      # заполнить B2B_LOGIN / B2B_PASSWORD для боевого режима
npm start                 # http://localhost:3000
```

Без `B2B_LOGIN`/`B2B_PASSWORD` бэкенд стартует в **демо-режиме** на `mockData.js` —
удобно разрабатывать фронтенд, не расходуя лимиты и не имея доступа к API.
